This is a database stress-testing application on python.

It supposed to be adaptable to various different database engines, currently have working engines for Postgresql, MariaDB and CockroachDB, YugabyteDB, Firebolt, ScyllaDB, TiDB, and SingleStore (memsql).

You've implemented:
 - sqeeel/database_modules, providing running the database engine and running queries against it using docker-based images;
 - sqeeel/template_instantiator module, that allows to generate queries that are scalable in size;
 - sqeeel/query_generator module that generates query templates based on a bison-style grammar parser tuned to the database calling database module hooks;
 - sqeeel/stress_engine, that applies each given template running stress loop over whole range of sizes;
 - runner application with CLI interface;
 - some limited unit tests in tests/ directory.

Also, in case of executor/compiler crash, it often does not require full docker restart as it self-heals.
Let's add self-healing wait before going to full recover, similar to what was done for ScyllaDB.

Actually, it looks like there are several issues:

1. When server crashes, but since the core dump is huge, the dumping takes time to trigger timeout. that causes detection of timeout or client-hang instead of crash; which misses recovery method -- causing several followup queries to get `stderr="ERROR 2269 (HY000): The database 'testdb' is not available for queries, as it is waiting for the Master Aggregator to bring it online.  Run SHOW DATABASES EXTENDED and visit https://docs.memsql.com/docs/database#database-states for more information.\n"` while database is in recovery mode.

2. When timeout/client-hang causes delayed server-side recovery response;  the instant health check succeeds, but in a few seconds the watchdog acts and database goes to recovery mode, leading to `"ERROR 2003 (HY000): Can't connect to MySQL server on '127.0.0.1' (111)\n"` errors happening for the followup queries.

That said, the simple health check + wait + health check is not sufficient to detect the correct recovery.

Please think about the whole execution flow and propose how exactly you could make query end detection robust, and validate the health after any non-"success" query -- not only after "crash" and "hung" for the singlestore, as this seems different from other databases here.

Please use the self.test_query instead of literal "SELECT 1" in health checks.
